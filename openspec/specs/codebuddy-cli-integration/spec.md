## Requirements
### Requirement: Subprocess launch contract

The system SHALL launch CodeBuddy Code CLI as a child process with the per-issue workspace path as its working directory, so that Symphony §9.5 Invariant 1 (`cwd == workspace_path`) holds before any agent-controlled command executes.

The CLI itself does NOT expose a `--cwd` flag (verified in Spike A, §1.5.4); the working directory MUST be supplied through the host's process-spawn API (e.g., Node.js `child_process.spawn(cmd, args, { cwd })`).

#### Scenario: CLI launched in workspace cwd

- **WHEN** the runner dispatches an agent attempt for issue `#101`
- **THEN** the CodeBuddy CLI subprocess is started with `cwd` equal to the absolute workspace path for `#101`
- **AND** the subprocess PID, launch command, and cwd are recorded in the structured launch log with field `issue_identifier`

#### Scenario: Launch aborts when cwd is outside workspace root

- **WHEN** the computed cwd is not a descendant of the configured `workspace.root`
- **THEN** the launch aborts before spawning the subprocess
- **AND** the attempt transitions to `Failed` with reason `invalid_workspace_cwd`

### Requirement: Multi-turn continuation via explicit session id

When `worker.kind === 'ssh'` the system SHALL preserve conversation context across continuation turns within one worker lifetime by using the CodeBuddy CLI `--session-id` and `--resume` flags, so that Symphony §7.1 continuation semantics ("continuation turns SHOULD send only continuation guidance to the existing thread") are satisfied under SSH's per-turn-subprocess model.

When `worker.kind === 'local'` the system SHALL NOT use this CLI flag path; the local mode is governed by the `sdk-multi-turn-worker` capability and uses the SDK session API instead.

Implementation note (SSH-only deviation from Symphony §10.3): under SSH, CodeBuddy CLI exits after each `--print` invocation rather than keeping the subprocess alive across turns. The SSH path MUST therefore spawn a new subprocess per turn and rely on the CLI's persistent session store (`~/.codebuddy/projects/<sanitized-cwd>/sessions/`) for context. The `-c/--continue` flag MUST NOT be used (it resumes the most-recent session globally, which causes cross-talk under concurrency); `-r <session_id>` is the only correct resume mechanism.

#### Scenario: First turn establishes session (SSH only)

- **WHEN** the runner starts turn 1 for a new issue and `worker.kind === 'ssh'`
- **THEN** the CLI is invoked with `--session-id <uuid>` where `<uuid>` is generated by the orchestrator
- **AND** the full rendered task prompt is passed as the positional argument
- **AND** the generated `<uuid>` is recorded as `agent_session_id` in the LiveSession state

#### Scenario: Continuation turn resumes by id (SSH only)

- **WHEN** turn N completes successfully and `worker.kind === 'ssh'` and the tracker issue state is still active
- **AND** turn count is below `agent.max_turns`
- **THEN** turn N+1 is invoked with `--resume <agent_session_id>` reusing the same id from turn 1
- **AND** only continuation guidance is sent; the full task prompt is NOT resent

#### Scenario: Concurrent tasks never share session id (SSH only)

- **WHEN** two issues are dispatched concurrently and both run under `worker.kind === 'ssh'`
- **THEN** each receives a distinct `agent_session_id`
- **AND** `-c/--continue` is never used by any invocation (only `-r <id>` is used)

#### Scenario: Local mode does NOT use the CLI flag path

- **WHEN** `worker.kind === 'local'`
- **THEN** the local SDK runner does NOT invoke the CodeBuddy CLI with `--session-id` or `--resume`
- **AND** continuation across turns is provided by the long-lived `Session` (see `sdk-multi-turn-worker` capability)

### Requirement: Structured runtime events parsed from NDJSON stream

The system SHALL invoke the CLI with `--output-format stream-json` and parse the resulting NDJSON stream (one JSON object per line) into structured runtime events mapped to Symphony §10.4 event semantics.

The CLI emits 5 native event shapes (verified in Spike A, §1.4.3):

- `{"type":"system","subtype":"init", ...}` — session started
- `{"type":"assistant", ...}` — assistant message (mid-turn or final)
- `{"type":"message","role":"user", ...}` — user input echo (only with `--input-format stream-json`)
- `{"type":"file-history-snapshot", ...}` — file tracking snapshot (tool-call byproduct)
- `{"type":"result","subtype":"success|error|...", "is_error":boolean, ...}` — turn completion

#### Scenario: session_started emitted from system:init

- **WHEN** the CLI emits an NDJSON line with `{"type":"system","subtype":"init"}`
- **THEN** a `session_started` event is forwarded to the orchestrator
- **AND** `session_id`, `model`, `permissionMode`, and advertised `tools` are copied into the event payload

#### Scenario: turn_completed emitted from result success

- **WHEN** the CLI emits `{"type":"result","subtype":"success","is_error":false}`
- **THEN** a `turn_completed` event is forwarded to the orchestrator
- **AND** the event payload contains `duration_ms`, `num_turns`, and `usage`

#### Scenario: turn_failed emitted from result error

- **WHEN** the CLI emits `{"type":"result","is_error":true}` or exits non-zero before any `result` event
- **THEN** a `turn_failed` event is forwarded to the orchestrator
- **AND** the event payload contains the error message and exit code when available

#### Scenario: Unrecognized output classified as malformed

- **WHEN** an NDJSON line cannot be parsed, or a parsed object has no recognized `type` field
- **THEN** a `malformed` event is emitted containing the original line as payload
- **AND** the worker continues running (malformed events do not abort the turn)

### Requirement: Token usage accounting uses absolute totals

The system SHALL extract token counters from the `result` event's `usage` object and treat them as absolute totals (not deltas), consistent with Symphony §13.5.

The `result` event's `usage` object provides (verified in Spike A, §1.4.5):

- `input_tokens` (absolute)
- `output_tokens` (absolute)
- `cache_creation_input_tokens` (absolute)
- `cache_read_input_tokens` (absolute)

Per-event `message.usage.*` on `assistant` events is also available and MAY be used for finer-grained accounting, but it is the same absolute total for the event's turn, not a delta.

#### Scenario: Delta computed against last reported total

- **WHEN** a new `turn_completed` event arrives with `usage.input_tokens = N`
- **AND** the previous `last_reported_input_tokens` for this session is `M`
- **THEN** the orchestrator adds `N - M` (not `N`) to its aggregate `agent_totals.input_tokens`
- **AND** updates `last_reported_input_tokens` to `N`

### Requirement: Agent-side tools exposed through MCP

The system SHALL pass an MCP configuration file to the CLI via `--mcp-config <path>` so that project-specific agent-side tools (e.g., `cnb_api`) are advertised to the in-session agent, filling the same role as Symphony §10.5's `linear_graphql` client-side tool extension.

The CLI accepts `--strict-mcp-config` to limit tool access to the configured MCP servers only; this flag MUST be enabled when `workflow.codebuddy.mcp_strict == true` (default: true).

#### Scenario: MCP config passed on launch

- **WHEN** the runner launches the CLI for a worker attempt
- **THEN** the launch command includes `--mcp-config <absolute-path-to-mcp.json>`
- **AND** the MCP configuration file declares at least the tracker-specific write tool (e.g., `cnb_api` for `cnb-tracker-backend`)

#### Scenario: Strict MCP mode blocks unlisted servers

- **WHEN** `workflow.codebuddy.mcp_strict` is `true`
- **THEN** `--strict-mcp-config` is appended to the launch command
- **AND** no MCP servers from user-global configuration are loaded

### Requirement: Runner supports streaming event callback

The `runCodebuddyTurn` function SHALL accept an optional callback for real-time event emission.

#### Scenario: onEvent callback invoked per NDJSON line
- **WHEN** `runCodebuddyTurn` is called with `onEvent` callback
- **THEN** each parsed `CodebuddyRunnerEvent` is passed to `onEvent` synchronously as soon as it is parsed, before being accumulated in the batch result

#### Scenario: onEvent is optional and backward-compatible
- **WHEN** `runCodebuddyTurn` is called without `onEvent`
- **THEN** behavior is identical to before (events only available in the returned result)

#### Scenario: onEvent failure does not abort the turn
- **WHEN** `onEvent` callback throws an error
- **THEN** the error is silently caught and the runner continues processing stdout normally

### Requirement: Runner supports dual mode (SDK + CLI fallback)

The runner SHALL select execution mode based on worker kind configuration.

#### Scenario: local worker uses SDK
- **WHEN** `config.worker.kind === 'local'`
- **THEN** the runner uses `@tencent-ai/agent-sdk` in-process to execute the agent turn

#### Scenario: SSH worker uses CLI subprocess
- **WHEN** `config.worker.kind === 'ssh'`
- **THEN** the runner falls back to the existing CLI subprocess path (spawn + NDJSON)

### Requirement: Event mapping from SDK messages

SDK async iterator messages SHALL be mapped to existing `CodebuddyRunnerEvent` types.

#### Scenario: system init message maps to session_started
- **WHEN** the SDK yields a message with `type === 'system'`
- **THEN** it is mapped to `{ event: 'session_started', payload: { sessionId, model, tools } }`

#### Scenario: assistant message maps to notification
- **WHEN** the SDK yields a message with `type === 'assistant'`
- **THEN** it is mapped to `{ event: 'notification', payload: { message, usage } }`

#### Scenario: result success maps to turn_completed
- **WHEN** the SDK yields a message with `type === 'result'` and `is_error === false`
- **THEN** it is mapped to `{ event: 'turn_completed', payload: { durationMs, numTurns, usage } }`

#### Scenario: result error maps to turn_failed
- **WHEN** the SDK yields a message with `type === 'result'` and `is_error === true` (excluding max turns exceeded)
- **THEN** it is mapped to `{ event: 'turn_failed', payload: { message } }`

#### Scenario: max turns exceeded still maps to turn_completed
- **WHEN** the SDK yields a result with `is_error === true` and errors containing "Max turns"
- **THEN** it is mapped to `{ event: 'turn_completed' }` (continuation semantics preserved)

### Requirement: onEvent callback compatibility

The `onEvent` callback introduced for EventBus integration SHALL continue to work with SDK mode.

#### Scenario: onEvent invoked per SDK message
- **WHEN** the SDK yields a message
- **THEN** after mapping to `CodebuddyRunnerEvent`, `onEvent` is called with the mapped event

### Requirement: Operator scheduler modes use subcommands
The system SHALL expose operator-facing scheduler modes as top-level subcommands.

#### Scenario: Check command validates the workflow
- **WHEN** an operator runs `codebuddy-auto check`
- **THEN** the system loads `WORKFLOW.md`, validates runtime configuration, and exits without starting the scheduler loop

#### Scenario: Daemon command starts the scheduler loop
- **WHEN** an operator runs `codebuddy-auto daemon`
- **THEN** the system loads `WORKFLOW.md` and starts the polling scheduler until shutdown

#### Scenario: Status command prints runtime status
- **WHEN** an operator runs `codebuddy-auto status`
- **THEN** the system prints a human-readable runtime status snapshot and exits

#### Scenario: Workflow path follows the mode command
- **WHEN** an operator runs `codebuddy-auto check ./ops/WORKFLOW.md`
- **THEN** the system uses `./ops/WORKFLOW.md` as the workflow path for that command

#### Scenario: Reload remains a command option
- **WHEN** an operator runs `codebuddy-auto daemon --reload`
- **THEN** the system reloads workflow/config before daemon ticks using the existing reload behavior

### Requirement: Legacy scheduler mode flags are removed
The system MUST NOT accept `--check`, `--daemon`, or `--status` as top-level scheduler mode selectors.

#### Scenario: Legacy check flag is rejected
- **WHEN** an operator runs `codebuddy-auto --check`
- **THEN** the system rejects the invocation before loading `WORKFLOW.md`

#### Scenario: Legacy daemon flag is rejected
- **WHEN** an operator runs `codebuddy-auto --daemon`
- **THEN** the system rejects the invocation before starting the scheduler

### Requirement: CLI fallback records persistent transcript events

When `worker.kind === 'ssh'`, each CodeBuddy CLI fallback turn SHALL record transcript events for the prompt passed to the CLI and the structured stream events parsed from CLI output when transcript persistence is enabled.

#### Scenario: CLI first-turn prompt recorded
- **WHEN** the SSH fallback starts turn 1 for an issue
- **THEN** the full rendered task prompt passed to the CLI MUST be recorded as a transcript event with role `user`
- **AND** the event MUST reference the issue id and turn index 1

#### Scenario: CLI continuation prompt recorded
- **WHEN** the SSH fallback starts a continuation turn for an issue
- **THEN** the continuation prompt passed to the CLI MUST be recorded as a transcript event with role `user`
- **AND** the event MUST identify the continuation turn index

#### Scenario: CLI stream events recorded
- **WHEN** the CLI emits structured stream-json events
- **THEN** recognized assistant text, system, message, and result events MUST be recorded as transcript events
- **AND** malformed or unrecognized events MUST be recorded with their raw payload when available

#### Scenario: CLI process failure recorded
- **WHEN** the CLI exits non-zero or the runner classifies the turn as timed out or failed
- **THEN** the failure MUST be recorded as a transcript event
- **AND** the event MUST include available exit code, stderr, timeout, or error message details
